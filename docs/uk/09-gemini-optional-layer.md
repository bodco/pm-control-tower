# 09. Опційний шар: Gemini як другий агент

## Навіщо другий агент, якщо є Claude Cowork

Дві реальні проблеми, які з'явились після року роботи:

1. **Обсяг історії.** У Notion накопичився рік мітингів і транскриптів. Claude Cowork не може за один запит опрацювати цей масив без втрати контексту. Кожен бриф на інженерну задачу перетворювався на окреме розслідування "про що ми домовлялись", а результат був недетермінований: два прогони давали різні констрейнти.
2. **Засмічення проєкту.** Корінь `~/work/acme/` заріс десятками згенерованих `.md` (29 файлів плюс папки investigations і reports) без структури. Ніхто не знав, що актуальне.

Рішення (вересень 2026): Gemini (Desktop на Mac, режим Spark, з Notion MCP) як **архіваріус і стратег** з гігантським контекстним вікном, який витягує сухі факти і обмеження з Notion у структуровані бріфи; Claude Cowork як **локальний інженер**, який виконує бриф у кодовій базі без інформаційного шуму. Взаємодія тільки через файли за протоколом.

Це саме опційний шар: без нього фреймворк повністю працездатний. Його функції частково закривають Decisions DB, сторінки Current State, Monthly Memory Digest і власний Notion MCP у Claude.

## Матриця ролей

| Зона | Gemini (Spark + Notion MCP) | Claude Cowork |
|---|---|---|
| Пам'ять і джерело правди | історія рішень у Notion, транскрипти за рік, Topics | поточна кодова база, локальні конфіги, стан БД, гілки, енви, логи, Sentry |
| Вхідний потік | сирі запити і багрепорти → визначає топік, актуалізує Topics DB | сфокусований бриф на 1-2 сторінки з файлової системи |
| Виконання | не пише код, не змінює файли проєкту, не чіпає термінал | пише код, досліджує, править баги, формує звіти |
| Файлова дисципліна | єдиний писар `.ai/tasks/`, `current.md`, QA-нот, `archive/` | єдиний писар `.ai/investigations/`, `.ai/reports/<id>.md` |
| QA | перевіряє рішення на відповідність домовленостям у Notion | оскаржує застарілі домовленості через `challenged_constraints` |
| Арбітраж | ескалює | ескалює |
| ПМ | пріоритети, дедлайни, клієнт, арбітраж; єдиний, хто редагує CONTRACT.md | |

Головне правило межі володіння: **Gemini не пояснює Claude, як влаштована система. Claude не реконструює, про що домовлялись.**

## Протокол `.ai/` (CONTRACT v1.0)

`CONTRACT.md` живе у `.ai/` кожного проєкту, у цьому репозиторії його немає: нижче витяг правил, достатній, щоб зрозуміти протокол і повторити його. Структура у корені кожного проєкту:

```
<project-root>/.ai/
  CONTRACT.md          протокол, пише тільки людина
  README.md            шпаргалка
  current.md           вказівник на активну задачу, пише тільки Gemini
  templates/           task / report / qa-note
  tasks/               бріфи, пише тільки Gemini      PROJ-1234-pse-navigation.md
  investigations/      технічний аналіз, пише Claude  PROJ-1234-auth-trace.md
  reports/             звіти Claude + QA-ноти Gemini  PROJ-1234-pse-navigation.md, .qa-1.md
  archive/YYYY-MM/     завершені задачі
  archive/pre-protocol/  усе, що було до протоколу, розкладене по категоріях
```

Ключові правила:
- **Один писар на файл.** Агент ніколи не редагує чужий файл, навіть щоб виправити статус. Виправлення = новий файл. Claude ніколи не оновлює `current.md`.
- **Сигнал = поява файлу**, а не зміна статусу: ідемпотентно, без race condition (агенти працюють на різних середовищах, спільна ФС - це обмін снапшотами).
- **Іменування** `<JIRA-KEY>-<slug>`, без дати в імені; без тікета `NOJIRA-<YYYYMMDD>-<slug>` з подальшим перейменуванням.
- **Життєвий цикл**: `ready_for_claude → in_progress → awaiting_qa → qa_passed → archived`, гілки `qa_failed` (макс. 2 раунди, потім `escalated`), `blocked`.
- **QA перевіряє** тільки відповідність домовленостям, DoD, Out of scope, повноту звіту. **QA не має права** виносити вердикт про технічну коректність, продуктивність, безпеку, правильність діагнозу: технічні сумніви - як питання, не як `failed`.
- **`challenged_constraints`**: Claude зобов'язаний підняти констрейнт, якщо код/БД/енви доводять, що він мертвий, з доказом; Gemini зобов'язаний відповісти `upheld` / `obsolete` (оновлює Decision Log як superseded) / `escalate`. QA-нота без цього розділу невалідна.
- **Decision Log** (Decisions DB у Notion) - пререквізит: констрейнти в бриф беруться звідти (дешевий lookup), а не зі свіжого сканування транскриптів; `notion-project-brief` дописує нові рішення після кожного обробленого мітингу.
- **Git і приватність**: `tasks/`, `current.md`, `investigations/` не комітяться (клієнтський контекст, імена); `CONTRACT.md`, `README.md`, `templates/` комітяться; `reports/` вибірково після вичитки. Жодних креденшелів у `.ai/`.
- **Гігієна**: одночасно живуть артефакти тільки активних задач; більше п'яти - протокол не працює як задумано.

Порядок дій Claude на старті: прочитати CONTRACT → `current.md` → (якщо `qa_failed`) останню QA-ноту → бриф → точково `sources` → працювати → звіт. Не починати, якщо статус не `ready_for_claude` або `qa_failed`.

## Скіли Gemini

### `notion-project-brief` (Context Archaeologist & Task Architect, CONTRACT v1.1)
1. Знайти або створити тему у Topics DB (немає теми → `confidence: low` + обов'язкове відкрите питання про верифікацію стану).
2. Витягнути контекст із транскриптів і документів строго в межах проєкту. Jira-ключ тільки якщо дослівно є у джерелі, ніколи не інтерполювати сусідні ключі. Один бриф = один результат для одного тікета.
3. Записати бриф за суворим шаблоном: frontmatter (id, jira, project, type, expected_mode, deadline, env, repos, branch, suggested_skill з дозволеного списку, sources з точними URL, confidence), секції Задача / Контекст (цитати з датами і спікерами) / Constraints і прецеденти (кожен з джерелом) / Вже пробували і відкинули / DoD / Out of scope / Відкриті питання.
4. Оновити `current.md` (single-writer).
Жорстка заборона: не стверджувати статус робіт як факт; твердження з транскриптів цитуються як думки спікерів `[Speaker, Date]`.

Запуск у Gemini Spark: "Підготуй бриф для проєкту acme по темі міграції платіжного провайдера" або "acme: клієнт пише, що вебхуки на стейджі відвалюються з таймаутом. Зроби бриф."

### `project-decision-qa` (Constraint Validator)
Читає звіт Claude, обробляє `challenged_constraints`, звіряє з Notion, пише `.qa-N.md`, ставить `qa_passed` + архівує або `qa_failed` з переліком правок. Запуск: "Зроби QA по PROJ-2362 у проєкті acme".

## Як це виглядає для ПМа

1. Приходить запит (клієнт, мітинг, власна ідея). ПМ каже Gemini одне речення.
2. Gemini кладе бриф у `.ai/tasks/`, оновлює `current.md`. ПМ за бажанням читає бриф (2 сторінки) і правит вручну тільки через Gemini.
3. ПМ каже Claude "візьми поточну задачу з.ai" (або Claude сам на старті сесії читає `current.md`). Claude виконує, пише звіт.
4. ПМ каже Gemini "зроби QA". Вердикт у `.ai/reports/`. Якщо `qa_failed`, Claude робить раунд 2. Після 2 раундів - три речення для ПМа: що вимагає Gemini, що зробив Claude, у чому конфлікт.
5. Архівація. Decisions DB поповнюється по дорозі.

## Коли НЕ вмикати цей шар

- Проєкт молодий, історія вміщується у Current State і Decisions - Claude сам прочитає Notion через власний MCP.
- Немає регулярних інженерних задач з брифами - протокол не має що обслуговувати.
- Немає дисципліни Decision Log - без нього кожен бриф дорогий і недетермінований, протокол просто перенесе хаос у файли.
- ПМ не готовий бути арбітром - два агенти без арбітра зациклюються.

## Поточний стан

Статус шару: бета, заморожено до успішного пілоту. Протокол розгорнуто у трьох проєктах (`acme`, `Delta`, `Gamma`). Корінь `acme` очищено: старі файли у `.ai/archive/pre-protocol/` за категоріями (code-reviews, investigations, specs, qa, deploys, docs, reports) з INDEX.md. Перші реальні задачі через протокол ще попереду; правило "перша задача маленька" в силі.

Рецензія назвала протокол "паперовим" і це чесна оцінка. Критерій успішного пілоту (прийнято): **3 послідовні інженерні задачі різного типу** (1 багфікс, 1 рефакторинг, 1 нова фіча) проходять повний цикл бриф Gemini → виконання Claude → QA Gemini → `qa_passed` без ручного виправлення синтаксису протоколу. До закриття пілоту цей шар не пропонується колегам.

Що треба закрити до пілоту:
- Схема Decisions DB (`Rationale`, `Alternatives rejected`, `Stated by`, статус `Disputed`, relation `Superseded By`) уже вирівняна з розділом 9 CONTRACT і описана у `02`; лишається перевірити, що `notion-project-brief` пише саме в ці поля.
- Одноразова міграція річної історії рішень не зроблена. Рекомендація рецензії: робити Gemini одним пакетним прогоном (контекстне вікно), результат як структурований список для заливки у Decisions через Notion API; Claude на такому обсязі втратить зв'язність.

Розширення, яке рецензія підтримала: `notion-project-brief` для не-інженерних задач (переговори по SOW, ескалаційні листи) через підтип `type: negotiation_brief | commercial_brief`.

## Що можна взяти без Gemini

Сам протокол `.ai/` корисний і з одним агентом: заборона `.md` у корені проєкту, `investigations/` і `reports/` як єдині місця для згенерованого, іменування по Jira-ключу, `archive/` за місяцями. Це знімає засмічення навіть без другого агента. Роль "стратега" тоді виконує сам ПМ через Decisions DB і Current State.
