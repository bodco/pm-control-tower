# 07. Операційний ритм ПМа з фреймворком

Цей документ описує, як виглядає реальний день, тиждень і місяць, коли автопілот працює. Принцип із `PM_Operational_Rhythm.md` залишається: важка аналітика на ранок, рутина на день, вечір без аналізу. Фреймворк лише зміщує межу: те, що раніше було "ранковою аналітикою" (пройти борду, перечитати чати, зібрати блокери), тепер уже лежить готове о 09:00.

## День

### До 09:00 (автопілот, людини немає)
- 07:05 Slack за вчора у Threads зі статусами. Треди, де останній автор не наш, позначені червоною крапкою.
- 09:01 Щоденний робочий звіт: що було вчора (календар, мітинги, треди, рух по Jira, Slack) і план на сьогодні. У Reports DB і локально.
- 09:12 Пошта з Mail.app у Threads; inbox-responder робить драфти відповідей на все, що чекає нас.
- Current State проєкту оновлено за останні 2 дні.

### 09:00-09:30 Ранковий ритуал (висока енергія, 15-30 хв)
1. Відкрити CONTROL TOWER.
2. Today's Reports: прочитати daily-work-report. Це замінює "пройти все руками".
3. Awaiting Reply: переглянути драфти inbox-responder. Три дії на тред: відправити (зі своїми правками), перетворити на тікет (`jira-management` або thread-ticket-sync), відкласти з Need Follow-up.
4. Inbox: обробити за 2 хв (Route / видалити).
5. Today / This Week + Overdue: обрати топ-3 дня. Це меню, не контракт. Тут видно все навантаження разом: обидва проєкти, компанійські справи, особисте. Якщо сума Effort level на сьогодні не вміщується у день, щось переноситься до того, як день почався, а не о 19:00.
6. Червоні сигнали: нові Sentry-помилки з prep, критичні ризики, дедлайни. Якщо щось горить, `acme-debug` або `sentry-assistant` одним реченням.

### 11:08 → 12:00 Внутрішній синк (через день)
- 11:08 daily-team-prep у Reports DB: хто чим зайнятий, рух по борді, блокери, теми зі Slack, action items, Sentry за 24 год, порожній блок "Мої нотатки".
- 11:45 ПМ дописує нотатки, 12:00 мітинг 10-15 хв, після нього одразу розблокувати те, що спливло (тікети, відповіді).
- Скіл сам визначає за конфігом, чи сьогодні синк-день (тиждень A Пн/Ср/Пт, B Вт/Чт).

### День (робоча зона)
- Async-відповіді пакетами 2-3 рази на день, не реактивно. Драфти вже є, тому пакет займає хвилини.
- Ведення артефактів по ходу: рішення у Decisions DB (одне речення, дата, джерело), зміна стану у конфіг, ризик у Risks через "перевір ризики" або вручну.
- Клієнт попросив "ще одну дрібницю"? `change-request`: відро A (облік, навіть безкоштовне), B (години, слот у плановій роботі або малий CR) чи C (торкається даних, грошей, безпеки: завжди CR). Extras Log наприкінці місяця показує, скільки goodwill пішло понад скоуп.
- Мітинг з клієнтом? Prep уже в Reports DB за 55 хвилин до. Після мітингу: "міт <url>" → двомовний звіт з action items на сторінці мітингу.
- Інженерні задачі: "ревʼю авторайзера <PR>", "знайди причину <симптом>", "що де задеплоєно", "порівняй бенефіціарів" + файли. Кожна - хвилини замість годин, результат у Reports DB або `.ai/reports/`.
- Думка або задача → Inbox (Quick Add).

### Кінець дня (нульова енергія, 5 хв)
- Виконане → Done у Tasks Tracker.
- Inbox triage.
- Один рядок: що завтра №1 (у Tasks Tracker або Inbox).
- Жодного аналізу дня: його зробить daily-work-report о 09:01.

## Тиждень

| День | Автопілот | Людина |
|---|---|---|
| Понеділок | 06:32 теми у Topics; 08:09 weekly-overview; 16:09 planning-prep | Ранок: прочитати weekly-overview, це "стан світу" на тиждень: що зроблено, відкриті питання, ризики, аутлук. Визначити фокус тижня. 17:00 планінг з клієнтом за prep |
| Вівторок | 16:02 status-prep | 17:00 Status Sync: прогрес, блокери, питання. Вікно деплою 08:00-10:00 COT для Authorizer, якщо є що промоутити (deploy-analysis показує) |
| Середа | лише щоденне | День для глибокої роботи: RCA, документація, стратегія, розмови з людьми |
| Четвер | 16:04 1-1 prep; 22:10 stability-scan | 17:00 1-1 з клієнтським ПМом: ризики, рішення, прев'ю наступного тижня. Друге вікно деплою |
| П'ятниця | 16:02 board health + review prep | Ранок: прочитати stability-scan (звіт + нові тікети), вирішити пріоритет дефектів. 17:00 Review: done list, демо, пайплайн. Ніяких деплоїв у п'ятницю |

Що змінилось порівняно з ритмом без фреймворку: prep і звіти більше не блок у календарі ПМа; тижневий огляд стає вхідним документом, а не вихідним; п'ятничний review отримує чистий борд без ручного проходу.

## Квартал і рідше

- Перегляд бібліотеки скілів: що не запускалось 90 днів, що варто заморозити або перейменувати; перевірка дата-маркованих фактів.
- Перегляд Cultural Profile клієнтської команди (нові люди, зміна ролей).
- Ревізія розкладу автопілоту під фактичний календар мітингів.
- Архівація проєктів, які закінчились (`project-lifecycle` closure: чекліст, handover pack, `status: archived`), одноразова міграція рішень для нових (`project-lifecycle` handover-in).
- Оновлення цього фреймворку і презентації для колег.

## Ритм для проєкту без повного стеку

Якщо на проєкті немає Sentry або репозиторіїв (наприклад Delta, Beta, клінічні дослідження), ритм скорочується до: колектори (Slack/пошта) → Threads → inbox-responder → prep до мітингів → weekly-overview → Decisions. У конфігу відповідні джерела "none", скіли їх пропускають. Мінімально життєздатний автопілот: 3 задачі (slack/mail sync, daily prep або client prep, weekly-overview).

## Прогін на оптимізацію (за запитом ПМ)

Час від часу ПМ просить прогнати систему на оптимізацію ("що тут можна оптимізувати"). Це не регулярний ритуал за розкладом, а запит на вимогу. Обовʼязкові пункти такого прогону:

0. **Технічний беклог Claude.** Пройти список у README розділ "Технічний беклог Claude" разом з ПМ: що робимо, що викидаємо, що чекає. Це єдиний момент, коли черга робіт Claude отримує людську пріоритезацію; без нього вона росте сама по собі і ніхто не вирішує, чи вона взагалі потрібна. Правило: пункт, який пролежав два прогони поспіль без руху, або отримує дату, або видаляється.
1. **Межа між адаптером і двигуном.** Пройти по проєктних адаптерах (`<slug>-*`) і перевірити, чи якийсь сценарій уже повторився на другому проєкті. Якщо так - кандидат на переведення у двигун. І навпаки: чи не завівся у двигуні проєктний факт, який має жити в конфігу.
2. **Дублювання скілів.** Два скіли, що роблять по суті одне й те саме, злити в один (як `topic-analyzer` + `weekly-topics-db-update` -> `topic-manager`).
3. **Мертві посилання і мовчазні дефолти.** Прогнати `scripts/lint_skills.py`.
4. **Розклад автопілоту.** Чи всі задачі ще потрібні, чи немає задач, які нічого не роблять місяцями.
